# LHG 开发思路蒸馏

本 Skill 记录从对话中沉淀下来的开发原则与决策偏好。每次调用时应先读取本文件，结合当前任务应用这些原则；若对话中产生新的原则，应更新本文件。

> **术语说明**：本 Skill 中的"美宜佳应用中心"即美宜佳开放平台的现行称呼，"开放平台"为旧称，两者指同一平台。

## 命名与领域表达

1. **同一张表存在多组请求/响应快照时，字段名必须加业务前缀区分**
   - 通用原则：不要把 `RequestPayload`/`ResponsePayload` 重复用于不同阶段的报文。
   - 例：付款推送侧用 `PushRequestPayload`/`PushResponsePayload`，资金平台返盘侧用 `ReturnResponsePayload`，避免覆盖、误读、对账困难。
   - 改名时要同步：实体、FreeSql/EF 更新、存储过程、建表脚本、变更脚本、日志字段引用。

2. **命名反映通用领域，不绑定具体业务方（美宜佳应用中心 / 开放平台场景）**
   - 在美宜佳应用中心（旧称：开放平台）接入场景下，一个应用通常只有一个 Webhook 接收入口，因此 Controller/通用 Service 不应带 `Ats`、`Myjjr` 等具体业务系统前缀。
   - 例：`AtsWebhookController` → `WebhookController`；`AtsWebhookReceiveService` → `WebhookReceiveService`。
   - 只有真正处理某业务方专属逻辑的服务才保留业务前缀，如 `AtsWebhookService`（处理 PMPQ01/ATS 付款返盘业务）。

3. **URL/资源命名优先遵循美宜佳应用中心（开放平台）规范**
   - 开放平台网关对资源段命名、URL path 拼接方式可能有特定限制（如 `web-hooks` vs `webhooks`），即使规范本身有争议，只要平台侧有限制，就先按平台要求实现。
   - 项目内部资源段仍按 REST 习惯用连字符拼接多单词。

## Webhook / 开放平台接入架构

4. **接收层与业务层严格分离（美宜佳应用中心 / 开放平台 Webhook 场景）**
   - 在美宜佳应用中心（旧称：开放平台）Webhook 接入场景下，Controller + 通用 ReceiveService 只负责：接收请求、Challenge 拦截、验签、解密、落库。
   - 平台要求必须在 5 秒内返回 HTTP 200，表示"接收成功"。
   - 具体业务回写、确认、状态更新交给下游 Job 异步处理，不在接收接口里同步执行。

5. **SDK 只封装无状态协议层（美宜佳开放平台 SDK 设计）**
   - 美宜佳开放平台 SDK 里只放：模型（`WebhookPushEvent`）、请求头（`WebhookHeaders`）、验签（`WebhookSignatureVerifier`）、解密（`WebhookDecryptHelper`）、Challenge 处理。
   - SDK 不放：依赖 DB 的日志写入、配置读取、业务过滤。这些属于业务层，不应反向污染 SDK。
   - SDK 也不应依赖具体日志框架（如 Serilog）；需要跨层透传的上下文（如链路 ID）用 `AsyncLocal` 抽象，而不是 `LogContext`。

6. **验签必须使用原始请求体字符串（美宜佳开放平台 Webhook 验签要求）**
   - 美宜佳开放平台 Webhook Action 不要绑定强类型 model 参数，应使用 `Request.Content.ReadAsStringAsync()` 读取原始 JSON。
   - 原因：框架模型绑定会改变字段顺序、空值、缩进等，导致平台验签失败；且绑定失败时无法保留原始内容排查。

## 第三方接口请求构造

7. **构造第三方接口请求时，字段严格使用数据库已落库值，禁止填充默认值**
   - 通用原则：不要在请求构造层用 `?? "默认值"`、`?? DateTime.Now`、`?? 0` 等兜底逻辑。
   - 原因：默认值会掩盖数据缺失问题，导致接口返回难以定位的错误；不同环境默认值可能不一致；违反"缺什么补什么"原则。
   - 如果字段确实需要默认值，应由数据写入方（存储过程、创建逻辑）在落库前保证，而不是在调用/推送时临时补。

8. **构造请求报文时必须完整映射所有字段，不能遗漏可空字段**
   - 通用原则：数据库实体有多少字段，请求模型就应该映射多少字段，即使是可空字段也要赋值（传 null）。
   - 不能因为接口文档标注"可空"就不在构造方法里赋值——数据库里该字段可能有值（如 `CheckCode`、`Memo`、`OurBankAccountNumber`），遗漏会导致接口收不到数据。
   - 构造完成后，逐一比对实体字段与请求模型字段，确认无遗漏。

9. **请求模型字段可空性必须与接口文档一致**
   - 通用原则：接口文档标注"可空"的字段，C# 模型必须用可空类型（如 `int?`、`DateTime?`），不能用非空类型（如 `int`）。
   - 原因：数据库字段为 NULL 时，赋值给非空类型会抛异常或被隐式填默认值，既不安全也掩盖数据缺失。
   - 请求模型与实体模型的可空性要对照检查，避免一边可空一边非空导致赋值异常。

10. **发起第三方接口调用前必须做本地必填校验**
    - 通用原则：按照接口文档的"非空"约束，在 HTTP 调用前逐项校验；同时补充业务上实际不可或缺的字段（如付款场景下的收方账号、户名、联行号）。
    - 校验失败直接返回业务错误，不要把明显不合格的请求发送到第三方，避免浪费调用和产生垃圾日志。
    - 错误信息要列出具体字段名，方便快速定位缺失数据。

11. **数据/校验类失败必须标记为不可重试的业务失败**
    - 通用原则：字段缺失、数据非法、业务规则不满足属于"明确失败"，不是"异常/可重试"。
    - 应直接置业务状态为失败终态，返回不可重试标记，避免进入 Job 重试队列无限循环。

12. **接口字段必填/可空以接口文档为准，不凭业务经验推断**
    - 通用原则：哪些字段必填、格式要求、长度限制必须逐字对照接口文档。
    - 业务上认为"应该必填"但接口文档标记为可空的字段，可以作为业务增强校验补充，但不能反向把文档必填字段忽略。

## 接口返回与错误码

13. **统一返回模型**
    - 开放平台相关接口统一返回 `OpenApiRetModel`（含 `code`/`msg`/`data`）。
    - 使用工厂方法创建：`OpenApiRetModel.Ok(...)` / `OpenApiRetModel.Fail(...)` / `OpenApiRetModel.Error(...)`。
    - 禁止裸写 `new OpenApiRetModel()` 或硬编码 `code = 16020200`。

14. **错误码/状态值必须区分"明确失败"与"异常/可重试"**
    - 通用原则：业务明确返回错误（如 `C00001`）和超时/网络/序列化异常必须分状态。
    - 例：ATS 推送状态 `PushStatus = 4` 表示"推送失败（有明确响应，不可重试）"；`PushStatus = 8` 表示"推送异常（超时/网络等，可重试）"。
    - 明确失败时直接置业务状态为失败终态；异常时保留原状，等待 Job 重试。

15. **错误码用枚举管理，按业务模块 region 隔离**
    - 扩展 `ApiRetCodeEnum`，按模块分 region（如基础金融、Webhook）。
    - 新增错误码时检查是否与其他值冲突。

## 日志与链路跟踪

16. **Service 层日志中间字段为空时，要到调用入口补 LogContext**
    - 通用原则：不要在每个 service 方法里重复传 `OrderNo`/`JobName` 等上下文字段。
    - 应在 Job/Controller 入口用 `LogContext.PushProperty` 推送业务上下文，同一 async 调用链下的 service、SDK 日志会自动继承。
    - 前提：Serilog 配置启用 `Enrich.FromLogContext()`，且 SQL Sink 的 `AdditionalColumns` 已映射这些字段。

17. **X-Correlation-Id 必须生成、透传、回写，但不要重复加头**
    - 通用原则：所有系统首次接收请求时检测 `X-Correlation-Id` 请求头，无则生成，并透传整个上下文，响应头必须回写。
    - 在项目中，如果已有全局 Filter（如 `ActionTraceAttribute`）统一处理，Controller 里不要再手动 `response.Headers.Add("X-Correlation-Id", ...)`，否则会冲突抛异常。
    - Job 等非 HTTP 入口：在作业开始时生成 `X-Correlation-Id`，通过 `LogContext.PushProperty("XCorrelationId", ...)` 进日志，通过 `AsyncLocal` 上下文（如 SDK 的 `CorrelationContextScope`）进 HTTP 请求头。

## 数据量与风险控制

18. **全量落库前必须评估数据量爆炸风险**
    - 当 topic 被多个系统共享（如所有系统都订阅 `PMPQ01`）时，不能无条件全量落库。
    - 应在写入日志前加过滤：根据 `srcSerialNo`、业务单据存在性、或配置规则判断是否是本系统数据。
    - 不属于本系统的数据直接返回 200，不落库。

19. **不确定的字段格式/数据量，先用真实数据验证**
    - 不要凭猜测设计过滤规则。先接入一笔真实推送，观察 `srcSerialNo` 格式、数据量级，再决定过滤策略。

## 数据模型与状态设计（通用）

20. **整型 Id 不作为业务查询/匹配键，优先用业务唯一键**
    - 数据库自增 Id 不适合作为业务查询、匹配或对外传递的键；应使用业务唯一键（如 `SrcBatchNo` + `SrcSerialNo`）。
    - 重试换号场景下，取当前实际使用的键（`LastSrcBatchNo`/`LastSrcSerialNo`）而不是原始键。

21. **推送/写库前校验关联数据完整性**
    - 调用下游或写库前必须校验依赖数据：非空、金额一致、必填字段存在等。
    - 校验失败按不可重试业务失败处理（参考 #11），不要走到下游接口或落半条数据。

22. **状态枚举必须在代码、实体注释、脚本注释、SP 注释中保持一致**
    - 新增或调整状态值时，同步更新实体 XML 注释、数据库字段注释/扩展属性、存储过程参数注释（三处同步的完整清单见 #37）。
    - 禁止代码和脚本各用一套语义；枚举注释与实现必须逐字一致。

## 工程实践

23. **代码改动后必须编译验证**
    - 修改后至少编译涉及项目，确认 0 错误后再继续下一步。
    - 优先用 `dotnet build` 或 VS 重新生成（.NET Framework 旧式 Web 项目用 VS MSBuild，不要用 dotnet build）。

24. **破坏性/兼容性变更优先停下来评估**
    - 新增字段、方法签名、接口、存储过程、DDL 变更时，必须考虑向后兼容、脚本同步、现有调用方影响。
    - 新字段、新参数一律可选 + 默认值；代码与脚本同改同发，不一致直接报错。
    - 必须破坏兼容（删字段、改签名类型）时立刻停止，先提示用户保存升级脚本并确认。

25. **改表字段名/新增字段必须同步检查存储过程和脚本**
    - 通用原则：只改实体和 FreeSql/EF 是不够的。
    - 必须全局搜索：建表脚本、变更脚本、存储过程、视图、触发器、动态 SQL、报表 SQL，确保字段名一致。

26. **删除字段前先确认所有调用方，而非仅凭"看起来没用"**
    - 搜索字段在代码、脚本、Job、文档中的全部引用。
    - 确认有调用方时，先决定替代方案（如 `PushEventId` → `SrcSerialNo`），再删除。

27. **接口常量必须严格对照接口文档，不要凭猜测**
    - 通用原则：版本号、枚举值、固定字符串等，必须与接口文档逐字核对。
    - 例：资金平台 `version` 要求 `"3+"`，写成 `"3"` 会导致接口响应异常。

28. **从具体项目蒸馏的原则必须标注适用场景**
    - 不要把平台特有限制（如美宜佳应用中心的 URL 规范、`web-hooks` 命名要求）当成通用最佳实践推广。
    - 也不要把通用设计原则（如 REST 资源命名）硬套到受平台限制的场景。
    - 在原则标题或正文中明确标注是"通用"还是"某平台/某环境特有"。

29. **工作区变更及时提交和推送，避免只存本地**
    - 代码、配置或 Skill 有重要变更后，尽快 `git commit`，不要等到一天结束才集中提交。
    - 每次会话或重要改动完成后，检查一次 `git status`，确认没有遗漏。
    - 提交后及时 `git push` 到远程；push 失败（网络、权限等）要显眼提醒，不能 silently 积压。
    - 如果变更较多，拆分为多个小提交，而不是一个超大提交。

30. **重载方法调用时显式命名参数**
    - 通用原则：当一个类存在多个重载、且参数类型/个数相近时，调用方必须显式使用命名参数（如 `msg:`、`JobName:`、`ex:`），避免编译器解析歧义或维护时看错参数位置。
    - 建议：如果重载越来越多，考虑在扩展类中给方法加后缀区分（如 `LogErrorModel`、`LogErrorTemplate`），从根本上减少歧义。

31. **长方法按职责拆分子方法，并统一收到 `#region Utilities`**
    - 当一个私有方法超过一屏或承担多个步骤时，按职责拆分。
    - 所有私有辅助方法统一放在 `#region Utilities` / `#endregion` 内；主流程方法（如 `Execute`、公开方法）放在 region 之前。

32. **删除冗余方法/字段时同步清理步骤编号、注释和调用链**
    - 删除方法后，更新主流程中的步骤编号和相关 XML 注释。
    - 删除字段后，同步检查实体、Service `.Set()`、脚本、Job 中的引用（与 #25、#26 联动）。

33. **AI 工具编辑文件后的编码收尾必须"每改一次、当轮即修"（通用，.NET Framework 项目）**
    - 事实：Trae Edit 工具每编辑一次就会剥离 UTF-8 BOM，且可能把 CRLF 改写成 LF。
    - 强时序：每次 Edit 修改 `.cshtml/.aspx/.vbhtml/.config` 等文本文件后，必须在**当轮**立即执行修复 + 复检；禁止"多轮编辑后最后统一补"，禁止只改不复检。否则会出现"上次修好了、这次又没了"的反复事故。
    - 修复命令统一用 .NET API，跨 PowerShell 版本可靠；禁止用 `Set-Content`（其 `-Encoding UTF8` 在 PS7 下不写 BOM，版本差异提醒本身会变成陷阱）：
      ```powershell
      $c=[IO.File]::ReadAllText($f); $c=$c -replace "`r`n","`n" -replace "`n","`r`n";
      [IO.File]::WriteAllText($f,$c,(New-Object Text.UTF8Encoding $true))
      ```
    - 复检：BOM 头三字节应为 `239,187,191`：`([IO.File]::ReadAllBytes($f)[0..2] -join ',')`。
    - 教训案例 1：连续多轮修改 CheckOrder.cshtml，第一轮补回 BOM 后第二轮 Edit 又剥掉且未复检，用户第三次才发现。规则若不绑定"每次编辑后立即处理"的时序，仅写"改之后要复检"这类软要求必然被遗漏。
    - 教训案例 2（根因升级）：用 .NET API 写入 BOM + CRLF 后，1 秒内文件又被还原为 UTF-8 + LF。排查后发现是 TraeWork/IDE 主进程长期未重启，其内部文件服务缓存了旧编码配置；关闭并重新打开 IDE 后，写入的 BOM + CRLF 保持稳定。因此：修复编码后若仍被还原，优先检查 IDE 是否长期运行过且期间修改过编码设置，必要时重启 IDE 再修复。

## 存储过程（SP）编写规范

34. **SP 主体必须用 `BEGIN TRY / BEGIN CATCH` 包裹，统一异常出口**
    - 通用原则：所有业务 SP 的主体逻辑放在 TRY 块里，CATCH 块统一组装错误信息并 `RAISERROR` 抛出，保证异常有统一出口。
    - 入口处声明 `@ModuleCode = OBJECT_NAME(@@PROCID)` 自动获取当前 SP 名，`@ModuleName` 写中文模块名，避免硬编码 SP 名；改名时无需同步修改字符串。
    - CATCH 块错误信息必须带 `ERROR_LINE()` 行号，格式如 `【SP名】执行异常 ，<原始错误信息> 行号：<N>`，便于快速定位。
    - CATCH 块必须写 `IF (@@TRANCOUNT > 0) ROLLBACK`；`BEGIN TRAN` 之后不能直接 RETURN 而不处理事务（事务悬挂会报"BEGIN 和 COMMIT 语句的数目不匹配"）。

35. **业务失败分支用 `RAISERROR` 抛给 CATCH 统一处理，不要静默 RETURN**
    - 通用原则：参数校验失败、防重复命中、源表无数据等"业务失败"场景，先 `SET @RetCode/@RetMsg` 给 OUTPUT 参数赋值，（注意：如果被外层过程循环调用需要考虑数据一致性是否要同时成功，再 `RAISERROR(@RetMsg, 16, 1)` 抛出），让 CATCH 块统一记录日志并上抛。
    - 原因：静默 `RETURN` 后调用方只拿到 RetCode，但外层 ADO.NET / Job 可能不会检查 OUTPUT，导致错误被吞；RAISERROR 能让上层 try/catch 显式感知失败。
    - 注意：严重级别用 16（普通业务错误），不要用 18+（系统级错误）。
    - 校验/查询逻辑尽量移到 `BEGIN TRAN` 之前；必须在事务内 RETURN 时先 ROLLBACK。

36. **动态 SQL 中获取自增 Id 必须用 OUTPUT 参数传出，不能用外层 `SCOPE_IDENTITY()`**
    - 通用原则：`sp_executesql` / `EXEC(@Sql)` 属于子作用域，外层调用 `SCOPE_IDENTITY()` / `@@IDENTITY` 都拿不到子作用域插入的 IDENTITY 值。
    - 正确做法：在动态 SQL **末尾**写 `SET @NewId = SCOPE_IDENTITY();`（同一作用域内取值），把 `@NewId` 作为 `OUTPUT` 参数从 `sp_executesql` 传出；EXEC 前 `DECLARE @NewId BIGINT;`（初始 NULL）。
    - 判断插入是否成功：用 `IF @NewId IS NOT NULL`，**不能**用 `IF @@ROWCOUNT > 0`——动态 SQL 末尾的 SET 语句会把 @@ROWCOUNT 重置为 1，原判断会失效。

37. **枚举字段的注释必须三处同步**
    - 通用原则：枚举字段的注释必须在以下三处保持一致：
      1. SP 常量声明区（列出全部枚举值 + 默认值）
      2. 建表脚本的字段行注释 + `sp_addextendedproperty`（表结构备注）
      3. 实体类注释（XML 注释或 `/// summary`）
    - 枚举值变更时，三处必须同步更新；建表脚本的 `sp_addextendedproperty` 需生成对应的 `sp_updateextendedproperty` ALTER 脚本。
    - 例：`SettlementModeCode` 从 `NULL` 改为 `'101'` 后，注释从"公司已付=601"更新为"101-直连支付 301-公司已付 102-手工制单"，SP 变量区、建表脚本字段注释、`sp_addextendedproperty` 三处同步。

38. **SP 改动后的同步检查清单**
    - 通用原则：改 SP 的常量/字段时，必须按以下清单逐项检查，不能只改一处：
      1. 常量声明区（是否新增/修改了变量）
      2. INSERT/UPDATE/SELECT 中的字段引用（值是否从硬编码改为变量）
      3. `sp_executesql` 参数声明列表（`N'@xxx TYPE, ...'`）
      4. `sp_executesql` 传参列表（`@xxx, @yyy, ...`）
      5. 头部变更记录（追加一行变更说明，SP 变更脚本保留原 Author/Create date/Description 三段，下方加"变更："段）
      6. 关联的建表脚本字段注释和 `sp_addextendedproperty`（枚举值是否同步）
      7. 关联的实体类注释（如有）

39. **修改 SP/脚本前必须先确认"哪个版本是生效版本"，以发版脚本目录为准（通用）**
    - 项目同时存在两套 SP 源：原版基线目录（如 `CyFinance/Procedures`）和发版脚本目录（如 `0.发版脚本/Vxxxx/`，ALTER 升级脚本，**这才是 DB 实际执行的**）。改动前先问清/查清目标库当前跑的是哪个版本。
    - 教训：直接改了原版 proc，而 DB 生效的是 V20260716 目录下的 ALTER 版本，导致白改 + 需 git 回滚。
    - 若报错文案/行为与原版源码对不上，第一反应应是"DB 里可能是另一个版本"，去发版脚本目录核对。

40. **拆分/重构发版脚本必须以基线源为内容底稿，并交付 diff 清单（通用）**
    - #39 说"DB 生效版本以发版脚本目录为准"——这仅指**执行顺序判断**，不代表发版脚本可作为**内容底稿**。拆分、重写、二次加工发版脚本时，内容必须来自基线源（或目标库 `sys.sql_modules` 实际定义），逐行对照。
    - 交付时必须输出与基线的 diff 清单（改了哪几处/各自原因），禁止只口头声明"逻辑一致"。diff 清单是证据，口头声明是断言。
    - 教训（2026-08-26）：把 4 个 SP 从旧合并发版脚本拆成单文件时照抄了旧脚本，而旧脚本本身就丢过 4 处逻辑（`订单已存在`校验、`TOP 1`、`StepIdNext=0`、`OrderNote AS UseTo`）。缺校验的 SP 一旦发版，会产生重复插单等数据事故，靠用户人工抽查才拦截。
    - 引申：**二手来源的残缺会沿着"复用"传播**。任何中间产物（发版脚本、生成的 DTO、复制的方法）被再次用作底稿前，先回权威源核对一次。

41. **多渠道路由类 SP 改造，INSERT 目标表和循环处理范围必须按渠道互斥（通用）**
    - 一个流程新增第二种清算/处理渠道时，路由规则：状态 UPDATE 覆盖全部支持渠道；但**写目标表必须按渠道互斥**（渠道 A 只插表 A、渠道 B 只插表 B），否则循环/INSERT 未过滤渠道会造成**双写**。
    - 教训：BatchSend SP 加美宜佳渠道（PayChannel=20）时，OAFlow 付款表 INSERT 和 ATS 循环都没按渠道过滤，工行单会同时落两张表；且 INSERT 引用了目标表不存在的列（PayChannel/ToLianHangHao），在 DB 直接报"列名无效"。
    - 检查清单：① INSERT 列清单逐一对照目标表真实结构（查 Tables/*.sql），禁止凭想象加列；② 每个写入路径的 WHERE 必须限定单渠道；③ 老渠道行为回归不变（WHERE 保持 `='1'`，不要顺手放宽成 IN）。

42. **SQL 循环处理临时表，统一用"SELECT TOP 1 ORDER BY 唯一键 + DELETE"模式（通用，LHG 偏好）**
    - 循环逐条处理时：`SELECT TOP (1) @var = Col FROM #tmp ORDER BY 唯一键` 取一条 → 处理 → `DELETE FROM #tmp WHERE 唯一键 = @var`，循环条件 `WHILE EXISTS (SELECT 1 FROM #tmp)`。
    - 相比 Id 计数游标（`WHILE @idx <= @max` + `WHERE Id = @idx`）的优点：无跳号/漏处理风险、清空即结束状态直观、不依赖临时表必须带自增 Id。
    - 唯一键用于保证 DELETE 精确删到刚处理的那条；处理失败路径走 RAISERROR 进 CATCH 回滚，不在循环里静默跳过。

43. **主从表插入时，从表的冗余字段必须从主表 SELECT 取值，不要用入参值或子查询**
    - 通用原则：从表如果冗余了主表的业务字段（如 OrderNo/SrcBatchNo/SrcSerialNo），INSERT 时应通过 `INSERT...SELECT FROM 主表 WHERE Id=@NewId` 直接取主表已落库的值。
    - 原因：入参值可能与主表实际落库值不一致（如触发器改写、默认值填充）；用入参写从表会产生主从不一致，后续按从表查询会漏数据。VALUES 中嵌套 `(SELECT ... FROM 主表)` 子查询可读性差，统一用 INSERT...SELECT。
    - 同时要求 INSERT...SELECT 列出从表全部非自增字段（全量字段），避免后续加字段时漏维护。

44. **主从表插入时，从表的审计字段（UpdateTime/UpdateUserId）首次插入也应填值**
    - 通用原则：从表 `AddTime/AddUserId` 标记创建动作，`UpdateTime/UpdateUserId` 在首次 INSERT 时也应填值（GETDATE() / @UserCode），不要留 NULL。
    - 原因：首次插入本身也是一次"写入操作"，留 NULL 会让 `UpdateTime` 字段在创建后到首次更新前为空，无法追溯"谁创建了这条记录"的完整链路；与主表保持一致的审计习惯。

45. **SP 中常量的变量化策略：已有同类模式时遵循一致**
    - 通用原则：当 SP 中已存在同类常量声明为变量的先例（如 `@PayTypeCode`、`@PayChannelAts`），新增常量（如 `@SettlementModeCode`）应遵循相同模式，在常量区声明并通过 `sp_executesql` 参数传入动态 SQL。
    - 判断标准：先看现有 SP 中同类常量怎么处理的——已有变量化的就跟变量化，已有硬编码的可以保持硬编码。保持一致优于每种都重新判断。
    - 注意：变量化后，动态 SQL 内必须通过 `sp_executesql` 参数传入，不能直接拼字符串名。

46. **SP 防御性编程：局部变量空值用 ISNULL 兜底，状态字段匹配用 = 具体值（通用）**
    - 局部变量空值判断：`SELECT` 赋值的局部变量有两种无效值——未命中保持 NULL、命中但字段空串变 `''`。`IF @Var IS NULL` 漏判空串会跳过下一级逻辑导致错位。强制 `IF ISNULL(@Var, '') = ''`（判空）/ `IF ISNULL(@Var, '') != ''`（判非空）；入参校验同理。
    - 状态字段匹配/UPDATE 用 `= 具体值`，禁止 `NOT IN (终态列表)`：① 三值逻辑陷阱——`NULL NOT IN (...)` = UNKNOWN，WHERE 吞掉该行；② `NOT IN` 只排除终态，会错误命中"未初始化/其他中间态"；`= 具体值` 只允许预期状态被处理。前提：状态字段 `NOT NULL DEFAULT 0`；UPDATE 乐观锁条件必须与 SELECT 匹配条件同一状态值。
    - 多级降级匹配（精确→宽泛→兜底）全 miss 时，RetMsg 必须输出全部入参匹配键的值，不能只报第一个，便于排查哪一级该命中却没命中。

## 异步 Job 与状态机

47. **状态机中间态必须配套异常回归路径**
    - 通用原则：只要状态机存在"处理中"（如 `PushStatus=2`）等中间态，就必须配套异常回归机制，否则实例重启、网络抖动都会让状态永远卡死。
    - 回归路径：外层 try/catch 兜底，任何未处理异常都必须把状态从中间态改回可重试态（如 `2 → 8`）。
    - 注意：catch 块内不能再抛异常，否则回归路径失效。

48. **异步 Job 回写操作的双重保护**
    - 通用原则：数据库回写是异步 Job 的最后一步，若失败却没有保护，状态就卡死了。必须两层保护：
      - 第一层：重试策略（如 Polly，3 次指数退避），处理瞬时故障（死锁、超时、网络抖动）
      - 第二层：兜底操作（只更新核心状态字段），保证重试都失败时状态不卡死，下次 Job 还能扫到
    - 关键约束：兜底操作不能再抛异常，否则状态就真的卡死了。

49. **并发敏感操作的乐观锁模式**
    - 通用原则：任何"读取旧值 → 计算新值 → 更新"的并发敏感操作，必须用乐观锁（`WHERE 旧值 = 读取值`）或数据库唯一约束保证不会重复生成。
    - 适用场景：幂等号换号（`WHERE RetryCount = 旧值`）、状态变更、计数增减等。
    - 补充：如果操作失败后果严重（如生成重复幂等号），建议同时加数据库唯一索引做最后防线。

50. **不要在 Job 处理阶段重复解析已在接收阶段落库的字段**
    - Webhook 接收阶段已将 `EventMsgNo` 等关键字段解析并写入日志表，Job 处理时直接用 `model.EventMsgNo`，避免再次反序列化 `RawBody`。
    - 通用化：同一数据在流水线前段已结构化落库的，后段直接读列，禁止重复反序列化原始报文——既省 CPU，又避免两处解析口径不一致。

## 第三方接口响应解析

51. **接口结构明确时用原生 JSON 逐层解析，结构不明确时深度搜索可作为过渡方案**
    - 通用原则：当接口文档准确、响应结构已确认时，优先按原生 JSON 层级逐项映射解析，每一层的字段名、类型、可空性都与文档对齐。
    - 当接口文档不准确或响应结构尚未确认（如初期开发文档有误）时，深度搜索/反射抓取字段可作为过渡方案快速验证，但结构确认后必须替换为逐层解析。
    - 原因：深度搜索在字段名微调或嵌套层级变化时容易失效，但开发早期文档不准确时逐层解析也会频繁报错。两者不是互斥关系，而是按阶段选用——先跑通、再定格。

52. **响应结果先收敛到有限状态，再映射到业务状态机**
    - 通用原则：接口返回码不应该无限分支。先按业务语义收敛到有限状态，再映射到业务状态机。
    - 常见收敛状态：成功 / 幂等冲突（换号重试）/ 明确失败（终态，不重试）/ 异常（超时/网络，可重试）。
    - 收敛后的处理逻辑不再依赖原始返回码，便于维护和扩展。

## 模型定义与命名规范

53. **JSON 反序列化模型的实体属性名必须与 JSON 字段名一致（仅允许大小写差异）**
    - 通用原则：使用 `[JsonProperty("msg")]` 映射时，C# 属性名必须与 JSON 字段名拼写一致（仅大小写差异），不要用同义词或别名。
    - 反例：`[JsonProperty("msg")] public string Message` —— 调用方会误以为 `.Message` 和 JSON `msg` 是不同字段，增加心智负担，且后续重命名时改动范围扩散。
    - 正例：`[JsonProperty("msg")] public string Msg`。
    - 例外：C# 保留关键字冲突时可用 `[JsonProperty]` 映射（如 JSON `class` → C# `Class`）。
    - 原因：JSON 字段名是对接方定义的"契约"，实体属性名是本地调用的"入口"，两者不一致会让每次调用都要在脑内做一次映射，且容易在重构时遗漏。

54. **按接口代号隔离目录+命名空间时，类名不加接口代号或业务前缀（避免信息重复）**
    - 通用原则：当通过目录和命名空间已隔离接口代号（如 `Models/OpenApi/ATS/Payment/PMSQ01/` + `namespace ...ATS.Payment.PMSQ01`）时，类名不要再加接口代号前缀（如 `PMSQ01PushRequest` → `PushRequest`，`AtsPubHeader` → `PubHeader`）。
    - 原因：命名空间隔离 + 类名前缀 = 信息重复。引用时 `PMSQ01.PushRequest` 已足够清晰，`PMSQ01.PMSQ01PushRequest` 反而冗余。
    - 判断标准：如果去掉前缀后，在当前命名空间下语义仍然明确，就应该去掉。
    - 注意：跨命名空间引用时如果类名太通用（如 `Mbs`、`Req`、`List`）可能冲突，需用 `using` 别名或完整命名空间引用，但这不构成保留前缀的理由——命名空间本身就是为解决冲突而设计的。
    - 适用场景：按接口代号/业务模块组织模型目录的 SDK/Library 项目。

55. **同接口代号下的请求/响应模型命名风格必须一致（含嵌套类名）**
    - 通用原则：同一接口代号（如 PMSQ01/PMPQ01/BDSQ06）下的请求和响应模型，类名、属性类型名、嵌套结构命名应保持一致风格。
    - 例：`ConfirmRequest` 的结构是 `Mbs → Pub(PubHeader) + Req → List`，那么同模块的 `CallbackRequest` 也应使用 `Mbs → Pub(PubHeader) + Req → List`，而不是 `FeedbackResult → FeedbackBody → FeedbackPub + FeedbackReq`。
    - 原因：风格不一致会增加阅读成本，让人误以为是不同结构；且后续如果需要提取公共基类或复用嵌套类，风格不统一会导致重复定义。
    - 实践：新增同接口模型前，先看同目录下已有模型的命名风格（根类名后缀 `Request`/`Response`、嵌套层名 `Mbs`/`Pub`/`Req`/`List`/`Detail`），保持一致。

56. **定义新模型时的"三对齐"检查（定义即对齐，避免后期大重构）**
    - 通用原则：定义新的 JSON 反序列化/序列化模型时，必须同时对齐三项，缺一不可：
      1. **JSON 字段名对齐**：C# 属性名 = JSON 字段名（仅大小写差异），通过 `[JsonProperty]` 显式映射并保持一致
      2. **命名风格对齐**：与同模块/同接口代号下已有模型的类名、嵌套类名、属性类型名风格一致
      3. **目录结构对齐**：按接口代号或业务模块隔离目录，类名不加前缀（参考条目 54）
    - 原因：如果定义时不对齐，后期重构的改动范围会随模型数量线性增长——本次重命名 `Message→Msg`、`AtsPubHeader→PubHeader`、`FeedbackResult→CallbackRequest` 共影响 20+ 文件，就是因为早期定义时未做"三对齐"。
    - 反思：为什么一开始没注意到？——因为第一行代码定下基调，后续模型会"跟随坏习惯"。如果第一个模型命名随意，第二个、第三个会惯性沿用，小问题积累成大改动。
    - 实践：接入新接口/新模块时，第一件事是确定目录结构、命名空间、类名风格，再写代码；每新增一个模型前，回看同目录下已有模型的命名风格。

## 播种性决策（元原则）

57. **播种性决策必须一次定对，避免事后大重构（最高优先级）**
    - 通用原则：命名（表名/类名/字段）、配置存放位置与读取方、服务职责归属、状态机流转等"播种性决策"，会像种子一样决定后续所有代码的惯性走向。动手写第一个模型/第一行配置/第一个枚举前，必须先把基调对齐，否则会埋雷成一次性 20+ 文件的大重构。
    - 判断标准：**这个决策是否会被后续大量代码"跟随"？** 是 → 动手前定死，不要"先写个大概后面再改"。
    - 反例：配置表命名 `Sys_OpenPlatformConfig → Sys_SdkConfig → Sys_MYJPlatformSDKConfig` 改了三遍，就是因为最初没把"系统前缀 + 业务域 + 实体类型"三层语义一次定对。
    - 具体播种性决策检查项：
      1. **命名三层语义**：`系统前缀 + 业务域 + 实体类型`（如 `Sys_` + `MYJPlatformSDK` + `Config`），禁止泛化（`Sys_SdkConfig` 无法区分是哪个 SDK）。
      2. **配置存放位置**：先想清"放哪、谁读、是否动态更新、是否敏感"，再落位（需要动态更新/敏感 → 数据库表 + JSON 扩展字段；简单开关 → JSON 文件）。
      3. **职责边界**：先划清层与层之间的边界（SDK 只管协议层，业务库只管业务，配置加载服务独立），再引依赖。
      4. **状态机完整流转**：先穷举从进入到终态的全部流转（含死信/告警/回归路径），再写代码。
      5. **验证前置**：改完立刻编译验证，不要攒到后期一起，避免类型/引用未接上才暴露。
    - 关系：本条是 #56"三对齐"的升维——#56 只管模型命名，本条适用所有播种性决策。

58. **状态机必须穷举完整流转再落码，注释与实现逐字一致**
    - 通用原则：定义枚举/状态机前，先穷举从进入到终态的全部流转，再写代码；配套"死信"终态 + 告警机制；注释必须与实现逐字一致。
    - 流转示例：`0-待处理 → 1-成功 / 2-处理中 → 3-幂等跳过 / 4-失败(可重试) → 超最大重试次数 → 5-死信(告警人工介入)`。
    - 死信要点：
      1. 可重试的失败态必须配套最大重试次数限制（`MaxRetryCount`）。
      2. 超限后转入"死信"终态，不再进入重试队列。
      3. 死信产生时触发告警（飞书/邮件/短信），通知人工介入。
      4. 存在"处理中"中间态时，必须配套异常回归路径（参考 #47），否则实例重启/网络抖动会卡死。
    - 注释一致性：枚举字段的注释必须在"SP 常量声明区 + 建表脚本字段注释/`sp_addextendedproperty` + 实体类注释"三处同步（参考 #37）。ProcessStatus 曾出现"注释与实际实现不符"，根因就是定义时没穷举全流转、注释没随实现同步更新。

59. **删除/迁移文件或资源时，必须同步清理所有引用它的地方，不能只删文件**
    - 通用原则：删除或迁移配置文件、资源文件、脚本时，不能只删文件本身，必须全局搜索并同步清理所有"引用/复制/打包"它的地方，否则会在编译/打包阶段才暴露。
    - 典型案例：把飞书配置从 `AppConfigs/appsettings.{development,production}.json` 迁移到数据库后，删了 JSON 文件但没删 `.csproj` 里的 `<Content Include="...json" CopyToOutputDirectory="Always">` 复制项，结果 MSBuild 复制阶段报 `error MSB3030: 无法复制文件...找不到该文件`。
    - 变更同步清理检查项（删除/迁移任何文件前逐项核对）：
      1. **项目文件引用**：`.csproj` 里的 `<Content>` / `<None>` / `<EmbeddedResource>` 复制项（`CopyToOutputDirectory`）
      2. **打包/发布脚本**：`pubxml`、CICD、msbuild target 里对该路径的引用
      3. **代码读取引用**：`File.Exists`、`ConfigurationBuilder.AddJsonFile`、`Path.Combine` 等读取该文件的代码
      4. **文档引用**：说明文档里对该文件路径的说明
      5. **部署配置**：部署机/发布机上的同名文件是否需同步下线
    - 关系：本条是 #25"改表字段名必须同步检查存储过程和脚本"的"文件级"推广——凡是"变更一个被多处引用的对象"，都要同步清理引用方。这也是 #57"播种性决策一次定对"的补救闭环：决策后迁移动摇，就必然带来同步清理负担。

60. **对"枚举型目录"放置实体目录前，先想清楚它会不会被消费方当作一个条目（通用）**
    - 通用原则：凡是被工具"递归枚举/扫描"的目录（IDE 技能目录、插件目录、路由模块目录、自动注册目录等），在其中放置任何**带内容子目录**前，必须问一句——"这个目录会不会被扫描器当作一个条目？"答案可能是，就绝不能放。
    - 事故（2026-09-04）：安装脚本把被替换的技能目录原地改名为 `<技能名>.backup-<时间戳>` 留在 `.trae-cn\skills\` 根下，TRAE 不认识 backup 后缀，递归扫描时把它当作一个可加载技能（frontmatter `name` 与正式技能相同），与 Junction 正式技能形成同名重复；实测 TRAE 调用技能时**命中了 backup 而非 Junction**，导致"改了仓库但技能不生效"。
    - 修复规则：此类"被替换/废弃的实体目录"必须移出扫描范围（如移到 `C:\AI-Skills\_backups\`）；扫描目录内只能存在"消费方应看到的条目"。
    - 关系：本条是 #57"播种性决策"的延伸——**备份/副本的落位同样是播种性决策**，放错位置会被下游机制惯性消费。

61. **验证状态判断用"存在性"而非"可访问性"（Test-Path 陷阱：断链 Junction 被误判成 MISSING）（通用）**
    - 通用原则：检查文件系统条目"是否存在"时，不能用 `Test-Path`——它对**断链的 Junction/符号链接返回 false**（目标已删），会把"存在但失效的链接"误判成"不存在"，导致诊断方向错误。
    - 正确做法：用 `Get-Item -Force -ErrorAction SilentlyContinue` 判存在（断链 Junction 也能拿到项），再分别判断 `LinkType` 和 `Target`。
    - 推广：任何"判断状态"的探针，都要区分"条目不存在 / 条目存在但内容失效 / 条目正常"三种情况，不能只探最终可访问性。
